## 这轮完成了什么

百度在校验提取码或获取分享下载地址时要求图片验证码，原实现会直接报错，且将校验接口的 `-12` 误当成提取码错误。本轮贯通“平台取图 → 界面人工输入 → 原会话提交 → 继续解析/下载”，实现错误输入后换图、取消、超时及请求隔离。

**这轮先完成验证码，百度临时转存兜底尚未实现。** 目前自动化、本地界面模拟验收均通过，但没有刻意触发真实百度验证码，也没有发布新的桌面 exe。不要把“模拟流程通过”写成“真实验证码已实测”。

## 协议与实现约束

- 提取码校验接口的 `-12/-62/-63` 进入图片验证码流程，`-9` 仍进入原有提取码输入提示；下载接口的 `-20` 使用下载验证码流程。每次流程初始请求后，最多再允许三次人工输入，连续失败会停止，等待用户手动重试。
- 取验证码使用 `/api/getcaptcha`，区分 `shareverify` 和 `share`。提取码校验提交 `vcode`，下载提交 `vcode_input`，均带 `vcode_str`。兼容独立 token、只返回 `genimage?TOKEN` 图片地址以及缺图片地址但有 token 的响应。其他未知响应保持明确失败，不猜测 token。
- 图片由原 HTTP 会话取回；只接受当前网盘源或百度 HTTPS 域名，并在重定向时重复验证。只允许 Go 能识别的 PNG/JPEG/GIF，最多 1 MiB，宽高不超过 2048。前端拿到 data URL，不接触登录 cookie、提取码或验证码 token。
- 回调在等待期间不持有队列或收件箱锁。提交后立即移出待输入列表，并发提交/退出不会向同一通道重复发送。每个请求独立 ID，旧提交不能写入新挑战。
- 前端每 500ms 查询待输入列表。后台在暂停/删除/关闭分享导致的 context 取消时移除请求；界面下次轮询收起。手动取消、验证码等待超时或三次输入失败均停止自动重试，避免持续弹窗。
- `core.Options.Interactive` 默认 false；cmd/pandl-cli 和 pandl-check 保持非交互行为，遇验证码明确报错，不会挂起等待不存在的界面。以后其他外壳需要显式启用，并实现查询/提交入口。
- 启动/重启时不恢复旧验证码；任务恢复会重新走平台会话。验证码不持久化、不打印日志。

协议核对仅参考上游自己的公开实现，没有复制其实现代码：

- [baidupcsapi：分享校验与验证码请求参数](https://github.com/ly0/baidupcsapi/blob/master/baidupcsapi/api.py)。
- [JDownloader：分享下载验证码的产品和提交字段](https://github.com/mirror/jdownloader/blob/master/src/jd/plugins/hoster/PanBaiduCom.java)。

这些是第三方平台的非公开接口实践，属于实现依据，不代表百度对接口长期稳定作出保证。

## 下一步实施顺序

1. **百度临时转存兜底**：保留直取优先；先明确哪些下载接口失败适合回退。登录过期、分享失效、无权限和验证码应各自提示，不直接把它们当作“需要复制文件”。
2. 选定并用隔离工具验证转存后的自有文件下载接口。已有资料表明网页版自有下载涉及主页签名，不能把分享签名直接套用；旧 PCS 下载形式也须真实验证。协议参考：[BaiduPCS-Go transfer.go](https://github.com/qjfoidnh/BaiduPCS-Go/blob/main/baidupcs/transfer.go)、[prepare.go](https://github.com/qjfoidnh/BaiduPCS-Go/blob/main/baidupcs/prepare.go)。仅完成了阅读核对，没有据此修改下载路径。
3. 临时对象按任务隔离：建议固定根目录下建立随机唯一子目录，先同步记录账号/目录所有权，再发转存请求，拿到新文件 ID 后再次同步保存。重试先检查已认领目录，避免远端已成功、本地超时后盲目重复转存。复用第三轮 `engine.PersistSource` 协议。
4. 清理只删除严格校验过的本任务临时对象，核对账号 UID；测试重启复用、重复完成、暂停后删除、转存超时、空间不足、切换账号、原文件不被删除。必须补充有界真实采样 + 清理验证，不能只靠本地接口模拟宣布完成。
5. 生成包含最新前后端的独立桌面测试版，使用 PANDL_DATA_DIR/PANDL_DOWNLOAD_DIR 隔离数据验收窗口、托盘、剪贴板与续传。完成后整理发布，再推进安卓；继续写下一轮交接。
