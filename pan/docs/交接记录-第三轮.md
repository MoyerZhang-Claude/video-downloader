## 保存协议与锁顺序

平台适配器在知道临时 ID 后执行：

```go
persist, _ := json.Marshal(updatedTaskSource)
if err := engine.PersistSource(ctx, persist); err != nil {
    // 仍返回 Source.Persist 和 error，不继续请求下载地址。
}
```

队列提供的回调会复制更新后的 Source，序列化完整任务快照，经原有 WriteFileAtomic（包含文件 Sync）写入成功后才返回。写入失败被标记为不可自动重试的保存错误，避免在存储故障期间继续产生云端副作用；用户解决存储问题后可以手动重试。

锁顺序必须保持：

1. 正常运行时先取得 `m.mu`，再取得 `m.saveMu`。
2. 后台 saver **取得 saveMu 之后才能取快照**；写文件时可以释放 mu，但在释放 saveMu 之前不得重新获取 mu。
3. 同步保存期间持有两个锁，等待旧写入结束，再写最新快照。普通队列操作会短暂等候这次磁盘写入。
4. Close 先等待下载/清理/计时器和 saver 结束，最后取得 saveMu 写最终快照。

不得改成“后台先取旧快照 → 释放 mu → 等 saveMu 再写”，否则旧快照可能覆盖已经同步保存的新 ID。也不得绕开 saveMu 并发写同一个 tasks.json.tmp。

旧平台适配器如果只返回 Source.Persist、不使用早期回调，队列仍会在 Resolve 返回后同步保存，之后才开始下载。123/夸克已经使用早期回调。直接调用 Resolver 的开发工具没有队列回调时仍按原有 Source.Persist 约定处理；本轮未改动实测工具。

## 剩余边界

- 服务器已接受转存、但尚未返回文件 ID 时，应用仍可能不知道需要清理哪个对象。这不能单靠本地写盘解决；原有残留扫描仍保留。
- 写盘本身失败且用户随即强制退出，无法保证新 ID 已在磁盘；现在明确停止后续操作、保留内存与返回记录并报错，不假装保存成功。
- 123 多个独立进程共享同一云端临时目录的协调与清理幂等性，仍是第二轮所述待验边界。
- 这次为关键 ID 同步写完整任务列表，超大任务量时的暂停时间尚未基准测试。常规进度不改为同步保存。
